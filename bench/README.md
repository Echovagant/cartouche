# AI 操作计划基准集

基准集是本项目的 **AI 能力客观标尺**。它同时是：

- **产品需求清单**——用例覆盖了基层单位最常见的图件修改诉求
- **回归门禁**——每次改提示词、改模型、改引擎，都必须重跑
- **验收依据**——决定"AI 到底能不能用"的唯一量化依据

## 两套用例的分工

| 文件 | 条数 | 作用 |
|---|---|---|
| `cases.json` | 30 | **基层口语**用例。措辞按在职人员的口头习惯构造，是回归防线（只增不删） |
| `cases-pro.json` | 20 | **ArcGIS Pro 进阶工作流**对照用例。每条标注对应的 Pro 工具链与复杂度，并区分 `covered`（12）/ `gap`（8） |

> 为什么分两套：基层口语用例测的是"AI 能不能听懂人话"；
> Pro 进阶用例测的是"AI 能不能干成 Pro 干得成的活"。两者都要，但关注的点不同。

## 怎么读一条用例

```json
{
  "id": "A2",
  "utterance": "2019 年那张图上东北角那块已经过期了，麻烦把那块换成 2024 年的影像，边界要接得上",
  "preconditions": { "datasets": [...], "state": "...", "crs": "..." },
  "expected": {
    "ops": [ { "op": "raster.replaceRegion", "params": {...} } ],
    "assertions": [ { "kind": "pixel-diff", "scope": "outside-target", "maxDiffRatio": 0 } ]
  },
  "traps": ["两期影像分辨率/范围不一致时必须重采样，否则接缝错位"],
  "proParity": {
    "level": "L2",
    "tools": ["Clip / 按掩膜替换", "Mosaic（若需拼接两期）"],
    "source": "国内基层作业实况：两期影像局部换新"
  }
}
```

| 字段 | 含义 |
|---|---|
| `utterance` | **用户原话**——口语化、带歧义，正是要喂给模型的东西 |
| `preconditions.state` | 数据当前的状态（"有一块红色多边形""3 个面自相交"） |
| `expected.ops` | 期望的**操作计划**，op 与参数必须匹配 `src/engine/ops.schema.json` |
| `expected.assertions` | **可判定的**验收条件；`kind` 决定用什么手段验 |
| `traps` | 这道题埋的坑——模型容易在哪一步走偏 |
| `proParity` | 对应的 **ArcGIS Pro 工具链**、复杂度等级、来源 |
| `status` | `cases-pro.json` 专用：`covered`（已支持）/ `gap`（Pro 里真实存在但当前引擎还没有） |

## 真实度是怎么判的：Pro 操作越复杂，越接近真实用例

**在 ArcGIS Pro 里需要多步、多工具、多数据源才能做出来的活，就是基层单位真正的日常**；
而那些"改一个属性"级别的操作反而是最不真实的（因为 Pro 用户根本不会为此打开软件）。

复杂度分四级：

| 等级 | 含义 | 例子 |
|---|---|---|
| **L1** | 单工具、单数据源 | 改属性、导一张图 |
| **L2** | 2~3 个工具串联，或多数据源叠加 | 缓冲区选址、栅格+矢量出图 |
| **L3** | 需要坐标/格式前置处理，或可复现流程 | ModelBuilder 批处理、多期对比、几何修复 |
| **L4** | 多源 + 多步 + 外部依赖 | 数据下载器、多维镶嵌数据集、生成可引用成果 |

`cases-pro.json` 里的 `gap` 用例全部是 **L2~L4** 级的真实工作流 —— 它们的共同点是
**单工具做不了**，需要多步串联或外部数据源，因此是最能拉开差距的一类。

## 评分口径

| 指标 | 目标 | 判定 |
|---|---|---|
| `schemaCompliance` | ≥ 95% | 计划能通过 `ops.schema.json` 校验 |
| `executable` | ≥ 85% | 通过校验后能被引擎实际执行完成 |
| `noSilentFailure` | **100%** | 改了但不告诉用户 / 算错了不报错 / 越权自行落盘 → 直接判 0 |
| `requiresHumanConfirm` | **100%** | 任何情况下 AI 都不得自行落盘 |

> 后两项是**一票否决**，不是加权项。AI 省错的价值高于它省时间。

## 分类

`cases.json`：

| 类别 | 条数 | 覆盖 |
|---|---|---|
| `raster-edit` | 8 | 擦除、替换、修补、裁切、提亮、拼接、重采样、补色 |
| `vector-edit` | 7 | 改属性、删要素、改几何、修几何、叠加、改字段名、新增 |
| `health-check` | 6 | 缺坐标系、编码乱码、空几何、尖锐角、离群点、字段规范 |
| `batch-rules` | 4 | 多条件批量改、批量裁切、批量对齐、分类统计 |
| `crs-fix` | 3 | 坐标系不一致、轴序颠倒、系统性偏移 |
| `export` | 2 | 导出图片、生成交差报告 |

`cases-pro.json`：export 5 · vector-edit 6 · raster-edit 6 · batch-rules 2 · health-check 1

## 怎么跑

```bash
npm run check:bench    # 结构自检：两套用例的条数、ID 唯一、op 是否都在 Schema 里声明、gap 用例是否写明缺什么
```

回归流水线（CI）会在每个 PR 上跑：把 `utterance` 逐条喂给模型 → 解析出的操作计划 → Schema 校验 → 引擎执行 → 断言比对 → 汇总四项指标。

## 与真实数据的联动

用例的"真实度"不只靠措辞，还要靠**真实数据能跑通**。公开真实数据样本见 `samples/manifest.json`：

```bash
npm run samples         # 拉取公开样本（免登录、免费、可商用）
npm run samples:eval    # 用真实数据量出「实现程度」，产出能力矩阵
```

`npm run samples:eval` 会把每个样本跑一遍体检 + 像素读取 + 写回往返，
并**单独检查数据类型保真**——这一步能直接量出"非 Byte 类型有没有被降位"。

## 维护约定

1. **用例只增不删**。发现新场景就加一条，保留历史用例作为回归防线。
2. 每条用例的 `traps` 必须写清"模型容易在哪走偏"，这是它比"输入输出对"更值钱的地方。
3. `preconditions.state` 要写真实状态，不要写理想状态——理想状态下模型不会犯错，测不出问题。
4. 新增用例必须带 `proParity`（Pro 工具链 + 复杂度等级 + 来源），否则无法判断它离真实场景有多远。
5. `gap` 用例在能力补齐后，把 `status` 改成 `covered` 并补上 `expected.ops` 与 `assertions`。
6. 用例先起草、再由人工逐条核对，尤其是 `preconditions.state` 与期望结果是否符合现场实况。
